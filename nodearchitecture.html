Every component, one card each

For revision — the same layers as above, explained a bit deeper.

V8 Engine

Compiles and executes your JS. Holds the call stack (what's running right now), the heap (object memory), and the garbage collector.

Only one thing runs on the call stack at a time — this is why a slow synchronous loop freezes your whole app, including timers that are already "due".

Node.js Bindings (C++)

The bridge between your JS and libuv. When you call an async API, this layer files the request with libuv and hands control back to V8 right away.

Built with V8's C++ API + node-api/internal bindings.

Timers

libuv keeps a min-heap of pending timers sorted by expiry time. On every loop tick it fires everything whose time has passed — never earlier, but possibly a bit later than requested.

Thread Pool

Real OS threads (4 by default) for work that's blocking at the OS level and has no async syscall. This is why heavy crypto.pbkdf2 calls can queue up behind each other.

Raise it with UV_THREADPOOL_SIZE (max 1024), set before Node starts.

OS Kernel Async I/O

Network sockets, pipes and TTYs are natively non-blocking at the OS level, so libuv just asks the kernel to notify it when data's ready — no worker thread spent waiting.

dns.lookup() is the odd one out: it uses the C library's blocking getaddrinfo, so it runs on the thread pool, not here.

The Event Loop

A fixed cycle of 6 phases: timers → pending callbacks → idle/prepare → poll → check → close callbacks, then back to timers. Each phase has its own callback queue and runs it to completion (or until a limit) before moving on.

Microtask Queues

process.nextTick() callbacks always run first, then Promise reactions (.then/.catch/.finally, resumed await). Both queues are drained completely — including anything newly added — after every callback and between every phase.

Ordering gotcha

setTimeout(fn, 0) vs setImmediate() at the top level: not guaranteed — depends on process startup timing.

Inside an I/O callback it's fixed: setImmediate() always wins, because you're already past the timers phase for that tick and check comes right after poll.

Trace it through one snippet

The same rules, applied line by line.

// app.js
console.log('1: start');

setTimeout(() => console.log('2: timeout'), 0);

setImmediate(() => console.log('3: immediate'));

Promise.resolve()
  .then(() => console.log('4: promise'));

process.nextTick(() =>
  console.log('5: nextTick'));

fs.readFile(__filename, () =>
  console.log('6: fs callback'));

console.log('7: end');
  1. 1 and 7 run first — plain synchronous code, straight down the call stack.
  2. Stack empties → microtasks drain: 5 (nextTick) before 4 (promise), always.
  3. Loop enters timers phase → 2 fires (its 0ms has already elapsed).
  4. fs.readFile was handed to the thread pool at line 1 — it finishes in the background and its callback (6) is queued for the poll phase whenever the OS thread signals completion.
  5. Loop reaches check phase → 3 fires.
  6. Every one of these steps is followed by a full microtask drain before the next line of the loop runs.
Note — steps 2, 3 and 6 race against real OS timing, so their exact order can shift between runs; 1, 7, 5, 4 never do.
